# AI 지식 게시판 발표 구성안

분석 기준: `README.md`, `READ.md`, `frontend/src/main.jsx`, `frontend/src/App2.jsx`, `frontend/src/components/post/PostListPage.jsx`, `frontend/src/api/client.js`, `backend/src/main/java/com/example/aiknowledgeboard`, `backend/src/main/resources/application.properties`, `backend/src/main/resources/db/migration/V1__init.sql`, `docker-compose.yml`, `infra/nginx/default.conf`를 확인했다.

## 발표 핵심 메시지

이 프로젝트는 "기본 게시판 기능을 먼저 완성하고, 그 위에 RAG, MCP, Agent를 실제 사용자 흐름에 연결한 개인 과제용 AI 웹 애플리케이션"이다.

발표에서 강조할 관점은 다음이 좋다.

- 단순히 LLM API를 한 번 호출한 것이 아니라, 게시글 작성/검색/질문/외부 도구 호출 흐름에 AI 기능을 붙였다.
- 2주 개인 과제 범위라서 복잡한 멀티 에이전트보다 설명 가능하고 데모 가능한 최소 구조를 선택했다.
- AI 기능이 실패해도 게시판의 핵심 CRUD는 유지되도록 기능 경계를 나눴다.

## 발표 전체 흐름

| 순서 | 섹션 | 권장 시간 | 핵심 메시지 |
|---|---:|---:|---|
| 1 | 프로젝트 개요 | 1분 | React + Spring Boot + PostgreSQL 게시판에 AI 응용 기능을 연결했다. |
| 2 | 주요 구현 기능 | 2분 | 인증, 게시글 CRUD, 댓글, 태그, 검색/페이징과 AI 기능을 구현했다. |
| 3 | 전체 아키텍처 구조 | 2분 | Frontend, Backend, DB, External API, DevOps 계층으로 나눴다. |

| 5 | 데모 | 3분 | 글 작성, RAG 유사 글/Q&A, MCP GitHub 조회, Agent 작성 보조를 보여준다. |
| 6 | 회고/한계/개선 | 2분 | MVP로 구현한 선택 이유와 다음 개선 방향을 설명한다. |

## 1. 프로젝트 개요

### 슬라이드 제목

AI 응용 기술을 활용한 지식 게시판

### 발표 내용

이 프로젝트는 사용자가 글을 작성하고 댓글로 소통하는 일반 게시판에 AI 기능을 결합한 웹 애플리케이션이다. 기본 기능은 회원가입, 로그인, 게시글 CRUD, 댓글, 태그, 검색, 페이징이고, AI 기능은 RAG 기반 지식 Q&A와 유사 글 추천, MCP 기반 외부 도구 호출, Agent 기반 작성 보조이다.

### 왜 이런 주제로 만들었는가

게시판은 CRUD, 인증, 검색, 댓글처럼 웹 서비스의 기본 요소를 모두 포함한다. 여기에 AI를 붙이면 "LLM을 별도 장난감 기능으로 호출하는 것"이 아니라, 실제 서비스 기능 안에서 AI가 어디에 들어가는지 설명하기 좋다.

### 발표 멘트 예시

> 저는 이번 과제에서 AI 지식 게시판을 만들었습니다. 목표는 거대한 AI 서비스를 만드는 것이 아니라, 게시글 작성과 검색이라는 익숙한 흐름 안에 RAG, MCP, Agent가 각각 어떤 역할로 들어가는지 직접 구현해 보는 것이었습니다.

### 프로젝트 기술 스택

| 영역 | 기술 |
|---|---|
| Frontend | React, Vite, Axios, vanilla-extract, lucide-react |
| Backend | Spring Boot 3.5, Java 21, Spring Security, JPA, Validation |
| Database | PostgreSQL, pgvector |
| AI | Spring AI, OpenAI Chat/Embedding 설정, PgVector VectorStore |
| MCP | JSON-RPC 스타일 요청/응답, GitHub API, Notion API 저장 도구 |
| DevOps | Docker Compose, Nginx, EC2 배포 스크립트/문서 |

## 2. 주요 구현 기능

### 2-1. 기본 게시판 기능

| 기능 | 구현 내용 | 코드 근거 |
|---|---|---|
| 회원가입/로그인 | 이메일, 닉네임, 비밀번호 기반 가입과 JWT 로그인 | `AuthController`, `AuthService`, `JwtTokenProvider` |
| 인증 처리 | Axios interceptor가 JWT를 붙이고, 백엔드 필터가 사용자 식별 | `frontend/src/api/client.js`, `JwtAuthenticationFilter` |
| 게시글 CRUD | 작성, 목록, 상세, 수정, 삭제 | `PostController`, `PostService`, `PostRepository` |
| 댓글 | 상세 화면에서 댓글 작성/삭제 | `CommentController`, `CommentService` |
| 태그 | 게시글 작성 시 태그 저장, 태그 검색 | `TagService`, `PostRepository.searchByTag` |
| 검색/페이징 | 제목/본문 키워드 검색, 태그 필터, 페이지 이동 | `PostListPage`, `PostService.list` |
| 공통 에러 응답 | validation, 권한 없음, not found 등을 통일된 JSON으로 반환 | `GlobalExceptionHandler`, `ErrorResponse` |

### 왜 기본 기능을 먼저 구현했는가

RAG, MCP, Agent는 혼자 존재하는 기능이 아니라 기존 서비스 데이터와 사용자 흐름 위에서 의미가 생긴다. 그래서 게시글과 사용자 인증을 먼저 만들고, 그 다음 게시글 데이터를 AI가 검색하거나 요약하도록 연결했다.

### 2-2. AI 활용 기능

| 기능 | 사용자 관점 | 내부 동작 |
|---|---|---|
| RAG 유사 글 검색 | 작성 중인 글이나 상세 글과 비슷한 기존 글을 찾는다. | 게시글을 VectorStore에 저장하고 similaritySearch로 관련 글을 조회한다. |
| RAG 지식 Q&A 봇 | 게시판 내용에 대해 질문하면 관련 글 근거와 함께 답변한다. | 질문을 벡터 검색하고 검색 결과만 근거로 ChatClient가 답변한다. |
| MCP GitHub 조회 | GitHub username을 입력하면 외부 정보를 JSON-RPC 방식으로 조회한다. | `github.getUser`, `github.getRepo` method를 GitHub API 호출로 매핑한다. |
| MCP Notion 저장 | RAG 챗봇 답변을 Notion 페이지로 저장한다. | `notion.saveRagAnswer` method가 Notion API `/pages`를 호출한다. |
| Agent 작성 보조 | 초안을 보고 태그 추천, 유사 글 검색, 필요 시 외부 도구 조회를 수행한다. | 최대 3회 도구 실행 제한을 두고 RAG/MCP/태그 추천을 조합한다. |

## 3. 전체 아키텍처 구조

### 전체 구조 다이어그램

```txt
[사용자 브라우저]
  |
  v
[React + Vite Frontend]
  - 로그인/회원가입
  - 게시글 목록/상세/작성
  - RAG Q&A 봇
  - AI 작성 보조 패널
  |
  v
[Nginx]
  - /api/* -> backend:8080
  - /*     -> frontend:80
  |
  v
[Spring Boot Backend]
  - auth: JWT 인증
  - post/comment/tag: 게시판 기능
  - ai.rag2: Spring AI VectorStore 기반 RAG
  - ai.mcp: JSON-RPC 외부 도구 호출
  - ai.agent: 도구 선택과 실행 루프
  |
  v
[PostgreSQL + pgvector]
  - users, posts, comments, tags, post_tags
  - vector_store
  - ai_logs, agent_memory, mcp_tool_logs
  |
  v
[외부 API]
  - OpenAI API
  - GitHub API
  - Notion API
```

### 왜 이런 구조로 나눴는가

Frontend는 화면 상태와 사용자 이벤트를 담당하고, Backend는 인증/비즈니스 로직/AI 연동을 담당한다. DB는 일반 게시판 데이터와 벡터 검색 데이터를 함께 저장한다. Nginx는 배포 환경에서 frontend와 backend를 같은 도메인 아래 묶어 주기 위해 사용했다.

이 구조의 장점은 각 계층의 책임이 분명하다는 것이다. 예를 들어 RAG 검색 방식을 바꾸더라도 React 화면이나 게시글 CRUD 전체를 바꿀 필요가 없다. MCP 도구를 추가할 때도 `McpService`의 method 분기와 외부 API client만 확장하면 된다.

### 요청 흐름 예시

```txt
게시글 작성
 -> React form submit
 -> Axios POST /api/posts
 -> JwtAuthenticationFilter에서 사용자 식별
 -> PostController.create
 -> PostService.create
 -> posts/post_tags 저장
 -> RagService2.loadIndex
 -> Spring AI VectorStore에 게시글 문서 저장
```

## 4. 각 AI 활용 기능, 기술, 아키텍처 구조

## 4-1. RAG 기능

### 구현 기능

- 게시글 작성/수정 시 게시글을 벡터 인덱스에 저장한다.
- 작성 중인 글 또는 상세 글 기준으로 유사 게시글을 추천한다.
- 게시판 지식 Q&A 봇에서 질문과 관련된 게시글을 찾아 근거 기반 답변을 생성한다.

### 사용 기술

- Spring AI `VectorStore`
- Spring AI `ChatClient`
- Spring AI `TokenTextSplitter`
- PostgreSQL + pgvector
- OpenAI chat/embedding 설정

### 아키텍처 흐름

```txt
게시글 저장/수정
 -> PostService.create/update
 -> RagService2.loadIndex(post)
 -> 기존 postId 인덱스 삭제
 -> title/content를 Document로 변환
 -> TokenTextSplitter로 chunk 분할
 -> VectorStore.add(chunks)
 -> pgvector vector_store 저장

질문/유사 글 요청
 -> RagController.similar 또는 RagController.chat
 -> RagService2.answer(query, excludePostId)
 -> VectorStore.similaritySearch
 -> SimilarPostResponse 목록 생성
 -> ChatClient로 요약/답변 생성
 -> summary + sources 반환
```

### 왜 이 구조를 선택했는가

처음부터 직접 SQL로 pgvector를 다루는 방법도 있지만, 현재 코드의 최신 흐름은 Spring AI `VectorStore`를 사용한다. 이 방식은 RAG 구현에서 중요한 "문서 저장, 검색 요청, score, metadata filter"를 표준화된 API로 다룰 수 있다.

게시글 본문을 그대로 하나의 벡터로 넣지 않고 `TokenTextSplitter`로 나누는 이유는 긴 글에서도 관련 있는 일부 문단이 검색될 수 있게 하기 위해서다. 게시글 단위 metadata에 `postId`, `title`, `authorNickname`을 넣은 이유는 검색 결과를 다시 게시판 UI의 출처 링크로 바꾸기 위해서다.

### 발표에서 조심할 점

README에는 과거 구현인 `post_embeddings` 중심 설명이 남아 있다. 실제 현재 코드에서는 `RagService2`가 Spring AI `VectorStore`를 사용하고, 설정상 테이블 이름은 `vector_store`이다. 발표는 현재 코드 기준으로 `RagService2`를 설명하는 편이 맞다.

## 4-2. MCP 기능

### 구현 기능

- `/api/ai/mcp/call` 하나의 endpoint로 JSON-RPC 스타일 요청을 받는다.
- `github.getUser`: GitHub 사용자 정보 조회
- `github.getRepo`: GitHub 저장소 정보 조회
- `notion.saveRagAnswer`: RAG Q&A 답변을 Notion에 저장
- 모든 MCP 호출은 `mcp_tool_logs`에 성공/실패 로그를 남긴다.

### 요청 예시

```json
{
  "jsonrpc": "2.0",
  "method": "github.getUser",
  "params": {
    "username": "openai"
  },
  "id": "demo-1"
}
```

### 아키텍처 흐름

```txt
React MCP 버튼
 -> aiApi.mcp()
 -> POST /api/ai/mcp/call
 -> McpController.call
 -> McpService.call
 -> jsonrpc 검증
 -> method 이름으로 도구 선택
 -> GitHub API 또는 Notion API 호출
 -> McpToolLog 저장
 -> JsonRpcResponse 반환
```

### 왜 JSON-RPC 스타일을 선택했는가

MCP의 핵심은 LLM 또는 Agent가 외부 도구를 일정한 프로토콜로 호출할 수 있게 만드는 것이다. 기능별로 REST API를 여러 개 만드는 대신, `method`와 `params`로 도구를 구분하면 "도구 호출"이라는 공통 흐름을 보여주기 쉽다.

과제 범위에서는 완전한 MCP SDK 서버보다 JSON-RPC 스타일의 최소 구현이 적절하다. 이유는 프로토콜의 핵심인 요청 ID, method, params, result/error 구조를 직접 설명할 수 있고, GitHub/Notion 같은 실제 외부 서비스 호출까지 보여줄 수 있기 때문이다.

## 4-3. Agent 기능

### 구현 기능

- 게시글 초안을 입력으로 받는다.
- 기본 도구로 태그 추천과 유사 글 검색을 수행한다.
- 초안 또는 의도에 GitHub 관련 내용이 있으면 MCP GitHub 조회를 추가한다.
- 최대 3회까지만 도구를 실행한다.
- 실행 단계와 결과를 응답에 포함하고, `agent_memory`, `ai_logs`에 기록한다.

### 아키텍처 흐름

```txt
React 작성 보조 버튼
 -> aiApi.agent({ draft, intention })
 -> AgentController.help
 -> AgentService.help
 -> chooseTools(draft, intention)
 -> recommend_tags
 -> search_similar_posts
 -> call_mcp_external_api 또는 summarize_draft
 -> buildFinalMessage
 -> AgentResponse 반환
```

### 왜 규칙 기반 Agent로 구현했는가

완전한 자율 Agent는 도구 선택이 더 유연하지만, 개인 과제 MVP에서는 디버깅과 데모가 어려워질 수 있다. 이 프로젝트는 "Agent가 도구를 선택하고 실행한다"는 핵심 흐름을 보여주는 것이 목적이므로, 도구 선택을 규칙 기반으로 제한했다.

`MAX_ITERATIONS = 3`을 둔 이유는 무한 루프를 막기 위해서다. Agent는 외부 도구와 LLM 호출을 포함하기 때문에 반복 제한이 없으면 비용, 응답 지연, 실패 반복 문제가 생길 수 있다.

## 5. 데모

### 사용할 수 있는 기존 스크린샷

현재 저장소에 `docs/screenshots/app-editor-ai.png`가 있다. 이 이미지는 게시글 작성 화면과 AI 작성 도우미 패널을 보여주므로 발표 자료의 최소 스크린샷으로 사용할 수 있다.

### 권장 데모 순서

1. 로그인
   - 회원가입 또는 기존 계정 로그인
   - JWT가 localStorage에 저장되고 이후 요청에 붙는다고 설명

2. 게시글 작성
   - 제목, 본문, 태그 입력
   - 저장 후 목록/상세 화면에 반영
   - 작성/수정 시 RAG 인덱싱이 함께 실행된다고 설명

3. RAG 유사 글 찾기
   - 상세 화면 또는 작성 화면에서 "유사 글" 실행
   - 유사 게시글 제목, 미리보기, 유사도 score, 출처 링크 확인

4. 지식 Q&A 봇
   - 게시판 내용에 대해 질문
   - 답변과 참고 게시글 출처 확인
   - "검색된 게시글만 근거로 답변하도록 설계했다"고 설명

5. MCP GitHub 조회
   - GitHub username에 `openai` 입력
   - JSON-RPC 요청으로 GitHub API 결과가 반환되는 것 확인

6. Agent 작성 보조
   - 작성 화면에서 초안 입력 후 "작성 보조" 실행
   - 추천 태그, 유사 글, 실행 step을 확인
   - "Agent가 도구를 순서대로 실행하고 결과를 종합한다"고 설명

7. 선택 데모: Notion 저장
   - Notion API 키와 data source가 설정되어 있으면 Q&A 답변을 Notion에 저장
   - 설정이 없으면 실패 응답을 보여주고, API key/권한 관리가 필요하다는 한계로 연결

### 데모 실패 대비 멘트

OpenAI API 키나 Notion API 키가 없는 환경에서는 외부 기능이 제한될 수 있다. 이 경우 데모에서는 GitHub Public API 호출과 기존 스크린샷을 중심으로 보여주고, OpenAI/Notion은 환경 변수 기반으로 연결되도록 구현했다고 설명한다.

## 6. 회고, 한계점, 개선 아이디어

## 6-1. 회고

### 잘한 점

- 기본 게시판 기능과 AI 기능을 같은 사용자 흐름 안에 연결했다.
- Spring Boot 계층 구조를 사용해 Controller, Service, Repository 책임을 분리했다.
- RAG, MCP, Agent를 각각 별도 패키지로 나누어 발표와 유지보수가 쉽다.
- Docker Compose와 Nginx를 넣어 로컬/배포 환경을 설명할 수 있다.
- AI 기능 실행 기록을 `ai_logs`, `agent_memory`, `mcp_tool_logs`로 남기도록 설계했다.

### 배운 점

- AI 기능은 모델 호출보다 데이터 흐름 설계가 더 중요하다.
- RAG는 검색 품질이 답변 품질을 크게 좌우한다.
- Agent는 자유도를 높일수록 제어와 예외 처리가 중요해진다.
- MCP는 도구를 많이 만드는 것보다 요청/응답 형식을 일관되게 만드는 것이 중요하다.

## 6-2. 한계점

| 한계 | 설명 |
|---|---|
| README와 실제 코드 일부 불일치 | README는 `post_embeddings` 기반 설명이 남아 있고, 실제 최신 RAG는 `RagService2`와 Spring AI `VectorStore`를 사용한다. |
| 테스트 갱신 필요 | `PostServiceTest`가 과거 `RagService` mock을 사용하고 있어 최신 `RagService2` 기준으로 갱신이 필요하다. |
| Agent 자율성 제한 | 현재 Agent는 LLM이 완전히 자유롭게 계획하기보다 규칙 기반으로 도구를 고른다. |
| RAG 품질 평가 부족 | 유사도 threshold, chunk size, 검색 결과 품질을 정량 평가하는 과정이 부족하다. |
| 권한/운영 기능 부족 | 관리자 권한, 게시글 신고, 모더레이션 같은 운영 기능은 MVP 범위 밖이다. |
| Notion/GitHub 외부 API 의존 | 외부 API key, rate limit, 권한 설정에 따라 데모 결과가 달라질 수 있다. |

## 6-3. 개선 아이디어

| 개선 방향 | 구체적 아이디어 |
|---|---|
| README 최신화 | `RagService2`, `vector_store`, `/api/ai/rag/chat`, Notion MCP 도구를 README에 반영한다. |
| 테스트 보강 | RAG Controller, AgentService, MCP GitHub/Notion 실패 케이스 테스트를 추가한다. |
| RAG 평가 | `eval_ragas_compare.py`를 활용해 chunk size, topK, threshold별 검색 품질을 비교한다. |
| Agent 고도화 | LangGraph 또는 상태 머신으로 도구 선택, 관찰, 재시도, 종료 조건을 더 명확히 만든다. |
| 권한 모델 확장 | 관리자, 작성자, 일반 사용자 권한을 분리하고 Auto-Mod Agent를 붙인다. |
| 배포 자동화 | GitHub Actions로 test/build 후 EC2에 자동 배포한다. |
| UI 라우팅 개선 | React Router를 도입해 목록/상세/작성 화면 URL을 분리한다. |
